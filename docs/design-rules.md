# Push 앱 디자인 규칙

- 버전: 1.0
- 작성일: 2026-11-16
- 상태: 초안
- 적용 범위: Push 앱(fo-mobile). 웹(fo-web)과 다른 점은 11장에 모았다. 데스크톱은 다루지 않는다.
- 관련 문서: [PRD.md](PRD.md), [feature-spec.md](feature-spec.md), [feature-map.md](feature-map.md)

화면을 새로 만들거나 고칠 때 따르는 규칙이다. 각 규칙에는 이유를 한 줄 붙였다. 이유가 문서화된 곳이 없는 규칙은 이유 없이 적었다. 규칙끼리 부딪히면 나중에 정한 쪽을 따른다. 아직 확정하지 못한 항목은 "(확인 필요)"로 표시했다.

"어디에 적용하나"가 적힌 규칙은 한 화면이 아니라 앱 전체에 적용된다. 같은 유형의 화면이 더 있으면 그 화면도 같이 고친다.

## 1. 원칙

- 앱은 iOS 네이티브 경험을 따른다. 글래스 느낌으로 애플 기본 앱처럼 보이게 한다. 안드로이드도 같은 구조로 지원한다.
  - 이유: 앱은 iOS 네이티브 경험이 중요하고, 애플 기본 앱 UI처럼 보여야 한다.
- 시스템이 제공하는 부품(토스트, 확인창, 메뉴, 시트, 선택 휠)은 직접 그리지 않고 네이티브를 쓴다.
  - 이유: 토스트처럼 알림용 네이티브 UI가 이미 있다.
  - 어디에 적용하나: 앱 전체.
- 화면이 이미 보여주는 말, 반복되는 제목, 긴 보조 문구는 쓰지 않는다. 판단 기준은 "이 줄이 없으면 사용자가 헷갈리는가"이다.
  - 이유: 당연한 문구는 필요 없다.
  - 어디에 적용하나: 앱 전체.
- 자동 저장처럼 당연한 동작은 알리지 않는다. 예: "기록했어요"는 보여주지 않는다.
  - 이유: 당연한 동작은 알릴 필요가 없다.
  - 어디에 적용하나: 앱 전체.
- 불필요한 아이콘과 색을 쓰지 않는다. 색이 필요 없는 곳은 검정이다.
  - 이유: 쓸데없는 아이콘과 색은 없앤다.
  - 어디에 적용하나: 앱 전체.
- 앱은 구직자와 현업자를 위한 것이다. 공고 수정은 웹에서만 하고 앱에서는 공고를 보내기만 한다. 예: "공고 보내기".
  - 이유: 공고 수정은 웹의 기능이고, 앱 사용자는 구직자와 현업자다.
- 화면의 원본은 Claude Design이다. 문서와 디자인이 다르면 디자인을 따른다.
  - 이유: 디자인에 있는 내용은 확정이다.

## 2. 용어

- 앱에서는 "에이전트"와 "봇"을 쓰지 않고 영어 "Bot"으로 쓴다. 예: Push Bot, 모아페이 Bot. UI 문구, 알림, 서버가 채팅에 쓰는 문장, 앱에 보이는 약관과 처리방침이 모두 해당한다.
  - 이유: 앱의 제품은 Bot이다. "에이전트"는 웹에서 같은 기능을 부르는 이름이다.
  - 어디에 적용하나: 앱 전체.
- "Bot"은 Bot 채팅방에서 Bot을 쓸 때만 쓴다. 그 밖의 AI 작업은 "AI"라고 쓴다. 예: "AI로 다듬기".
  - 이유: Bot 채팅방에서 하는 것만 Bot을 쓰는 것이다.
- 채팅방에서 처리하는 일은 "Bot한테 보내기"라고 쓴다. 예: 서류 고치기 대신 "Bot한테 보내기".
  - 이유: 서류 고치기 같은 일은 Bot 채팅방에서 할 수 있다.
- 프로필 파일은 "Push 프로필"이라고 쓴다. "이력서 파일"과 파일 확장자는 쓰지 않는다.
- "내 프로필"(기본)과 "지원용 프로필"(Push 서류)은 다른 것이다. 하나를 다른 하나처럼 설명하지 않는다.
- "요금제" 대신 "플랜"을 쓴다.
- "사용량"은 월 사용 한도이고, "크레딧"은 따로 사는 것이다. 한도를 다 쓰면 "이번 달 사용량을 모두 썼어요"라고 알린다.
- "대화에서 찾기" 대신 "채팅에서 찾기"를 쓴다.
- 작업을 멈출 때는 "중지"를 쓴다. 예: "작업을 중지했어요".
- "그만하기"와 "취소" 대신 "닫기"를 쓴다. "완료" 대신 "적용"을 쓴다.
- 우측 라벨 "자동"은 항목 이름에 넣어 "자동으로 변경"처럼 쓴다.
  - 어디에 적용하나: 앱 전체.
- 운영자와 개인정보 보호책임자는 채영준이다. 약관, 처리방침, 이름이 나오는 모든 곳이 같다.

## 3. 레이아웃·색·글자

### 배경과 헤더

- 한 화면은 배경색 하나만 쓴다. 헤더, 필터 행, 목록, 섹션, 토글 바 사이에 투톤을 만들지 않는다.
  - 이유: 나눌 이유가 없는 곳에서 배경이 나뉘면 안 된다.
  - 어디에 적용하나: 앱 전체.
- 헤더는 네이티브 Apple 스택 헤더처럼 화면과 같은 배경에 살짝 투명하게 둔다.
  - 이유: 애플 네이티브 스택은 헤더가 약간 투명한 방식이 있다.
- 홈을 스크롤하면 상단 바를 투명하게 한다.
- 버튼을 담는 영역에는 자기 배경색을 주지 않는다.
  - 이유: 영역에 색이 있으면 위쪽과 투톤이 된다.
- 위아래 안쪽 여백은 같게 한다. 아래에 공간이 더 필요하면 마진으로 준다.
- 시트와 모달의 높이는 내용에 맞춘다. 빈 공간을 남기지 않는다.
  - 이유: 빈 공간이 너무 크면 어색하다.
  - 어디에 적용하나: 모든 시트와 모달.
- 시트와 모달 배경의 투명도는 너무 비치지 않는 하나로 맞춘다.

### 색

- 강조색은 주 버튼과 선택된 상태에만 쓴다. 그 밖의 글자와 아이콘은 검정(다크 모드에서는 흰색)이다.
  - 이유: 색이 필요 없는 곳은 검정으로 둔다.
- 배지는 모양과 회색을 하나로 통일한다. 상태는 글자로 알린다.
  - 이유: 모든 배지의 색이 제각각이면 이상하다.
  - 어디에 적용하나: 앱 전체.
- "합격" 배지만 검정이다. 다크 모드에서는 흰색이다. 수락함 배지를 검정으로 할지는 정하지 못했다 (확인 필요).
- 차단한 사람 행처럼 의미 없는 곳에는 색을 넣지 않는다.

### 글자

- 굵은 글씨는 제목과 꼭 눈에 띄어야 하는 글에만 쓴다. 오류 문구, 본문, 힌트는 보통 굵기다.
  - 어디에 적용하나: 앱 전체.
- 글은 단어 중간에서 끊지 않는다(hangul-word). 한 글자만 다음 줄로 넘어가거나, 겹치거나, 잘리지 않아야 한다. 긴 이름과 큰 글자 크기에서도 같다.
  - 이유: 글자가 깨지고 줄바꿈이 어색하면 읽을 수 없다.
  - 어디에 적용하나: 앱 전체.
- 폰트는 Noto Sans KR이고, 굵기는 숫자가 아니라 디자인 토큰으로 쓴다.

### 아이콘

- 메뉴 아이콘은 정렬 아이콘처럼 정돈된 SF Symbols 계열로 맞춘다.
  - 이유: 기존 메뉴 아이콘이 어색하다.
- 더보기는 ⋯ 아이콘이다. 햄버거 아이콘은 쓰지 않는다.
- 앱 아이콘을 흉내 낸 그림("P." 같은 글자나 로고)은 화면에 넣지 않는다. 필요하면 글자만 보여준다.
- 마스코트는 실제 마스코트를 쓴다. Bot 목록의 마스코트는 움직인다.

## 4. 버튼·입력

### 버튼

- 헤더와 내비게이션의 버튼(뒤로, 닫기, 더보기, 계정)만 글래스 버튼이다. 그 밖의 버튼은 모두 일반 버튼이다.
  - 어디에 적용하나: 앱 전체.
- 화면 안의 보조 버튼은 글래스가 아니다. 예: "다시 시도", "크레딧 구매", "차단 해제", "프로필 수정", "공유".
- 헤더 버튼은 글래스이고 회색 배경을 쓰지 않는다.
- 헤더 옆에 붙는 버튼은 높이를 이웃한 버튼에 맞춘다. 예: "모두 읽음"은 뒤로가기 버튼과, 검색 "닫기"는 입력창과 높이가 같다.
- 보조 버튼은 이웃한 버튼과 구분되게 한다. 예: "차단 해제"는 눈에 띄는 일반 버튼이다.
- 시트와 모달의 버튼은 아래 푸터(액션 영역)에 둔다.
- 일반 모달에 닫는 버튼이 필요하면 푸터에 "닫기" 글자 버튼을 확인 버튼 왼쪽에 둔다. 예: "닫기 · 적용".
- 검색의 닫는 버튼 이름은 "취소"가 아니라 "닫기"다.

### 입력

- 입력창은 iOS 네이티브 글래스 입력이다. 검색, 자료 목록, 팔로잉 목록의 입력도 같다.
  - 어디에 적용하나: 앱 전체.
- 키보드가 열리면 입력창은 키보드 바로 위에 있다.
- 채팅 입력은 한 줄로 늘어놓는다. 순서는 + 버튼, 입력, @, 전송 버튼이다. 입력은 최대 다섯 줄까지 늘어나고 그 뒤에는 안에서 스크롤한다.
  - 이유: 입력에 최대 세로 길이가 있어야 한다.
- 채팅 입력에는 권한이나 자동 같은 모드 선택을 두지 않는다.
- 모달 안에서 검색해도 모달 헤더와 닫기 버튼은 그대로 둔다. 검색 결과가 없으면 헤더를 뺀 영역의 세로 가운데에 안내를 보여준다.
  - 이유: 검색 중에 헤더가 사라지면 닫을 수 없다.

## 5. 모달·시트·얼럿·토스트

어디에 적용하나: 앱 전체. 모든 모달을 아래 종류로 나눈다.

### 종류

- 페이지형 모달은 자기 내용을 둘러보는 곳이다. 전체 목록, 상세, 입력칸이 여러 개인 폼이 해당한다. 닫기 버튼(X)이 있다.
- 일반 모달은 짧은 질문 하나에 답하거나 한 가지를 확인한다. X도 "취소"도 없다. 확인 버튼 이름은 "적용"처럼 하는 일을 말한다.
  - 이유: 닫기 X는 페이지형 모달에만 있다.
- 얼럿은 경고와 되돌릴 수 없는 삭제 확인에만 쓴다. 네이티브 얼럿을 쓴다. 예: "삭제".
  - 이유: 얼럿은 경고창이다.
- 얼럿 밖의 확인과 선택은 일반 모달이다. 동의 화면도 얼럿이 아니라 일반 모달이다.
- 모달 위에 모달을 겹치지 않는다. 얼럿은 모달 위에 띄워도 된다.
- 시트, 액션 시트, 컨텍스트 메뉴, 토스트는 네이티브 부품을 쓴다.

### 무엇을 쓸까

| 상황 | 쓰는 것 | 예 |
|---|---|---|
| 값 하나를 정해서 저장한다(짧은 고정 목록) | 휠 모달 | 언어, 테마, 커리어 상태 공개 범위 |
| 날짜나 시간을 정한다 | 휠 모달 | 면접 일정 |
| 흐름 중에 사용자에게 묻고 선택지를 준다 | 일반 모달. 질문 하나당 모달 하나 | Bot 흐름의 관문 |
| 질문이 여러 개다 | 질문마다 모달을 나눈다 | 진행 방식, 산출물, 자료 고르기를 각각 따로 |
| 동의를 받는다 | 일반 모달 | 참고 자료 동의 |
| 전체 목록이나 상세, 여러 칸 입력 | 페이지형 모달 | 전체 게시글, 자료 상세 |
| 늘어날 수 있는 목록 | 최근 3개와 "전체 보기". "전체 보기"는 페이지형 모달 | 제안, 서류, 링크, 북마크 |
| 경고하거나 삭제를 확인한다 | 얼럿 | 서류 삭제 |
| 값을 보여주기만 한다 | 화면의 평문 | 설정 행의 현재 값 |
| 짧은 결과를 알리고 되돌릴 수 있다 | 네이티브 토스트 | 삭제 후 되돌리기 |
| 항목의 메뉴를 연다 | 네이티브 메뉴나 액션 시트. 길게 누르면 iOS 컨텍스트 메뉴 | Bot 목록 길게 누르기 |
| 필터를 고른다(복수 선택, 짧은 목록) | 토글이나 칩이 있는 일반 시트 | 경력, 직군, 고용형태, 기술 스택 |
| 필터를 고른다(긴 목록) | 스크롤하는 일반 시트. 휠이 아니다 | 지역(시·도 다음 구) |
| Bot 작업 결과나 오류 | 채팅 말풍선 (7장) | 서류 수정 결과 |
| Bot이 바꾼 내용을 검토한다 | 말풍선 안에서 "되돌리기"와 "적용" | 7장 |
| 앱 화면에서 한 동작이 실패한다 | 얼럿 (확인 필요: 토스트와의 경계) | 지원 실패 |

### 세부

- 휠 모달 화면에는 현재 값만 보이고, 고르는 일은 모달 안에서 한다.
  - 이유: 언어 같은 선택은 휠 모달로 쓰는 것이 보통이다.
- 셀렉트형 모달은 짧은 고정 목록에서 하나를 고를 때만 쓴다. 보여주기만 하는 값은 평문으로 둔다.
- 필터처럼 여러 개를 고르는 목록은 휠이 아니라 토글이 낫다. 지역 필터도 휠이 아니라 이전의 스크롤 목록이다.
  - 이유: 복수 선택이 겹치면 이전 UI와 토글형이 더 낫다.
- 메뉴는 대상의 미리보기를 함께 띄운다. 예: Bot 목록을 길게 누르면 Bot 미리보기를 같이 보여준다.
- 파일을 크게 봐야 할 때는 모달 위에 모달을 열지 않고 파일 뷰어 화면을 연다.
- 캘린더는 모달로 분리하고, 화면에는 그날의 목록만 남긴다.
- 토스트와 확인창은 네이티브 UI를 쓴다. 오류도 화면 안에 붉은 박스로 그리지 않는다.

## 6. 목록

- 시트와 모달 안의 목록은 늘어날 수 있으면 최근 3개와 "전체 보기"로 줄인다. 예: 제안 보내기 시트에서 서류가 4개 이상이면 3개와 "전체 보기"를 보여준다.
  - 이유: 모달이 길어지면 보기 나쁘고 쓰기 어렵다. 늘어나거나 추가할 수 있는 목록은 길어졌을 때를 생각해야 한다.
  - 어디에 적용하나: 앱 전체. 제안, 게시글, 서류, 링크, 북마크 등 늘어날 수 있는 모든 목록.
- "전체 보기"는 닫기 버튼이 있는 페이지형 모달이다. 안에서 끝까지 스크롤하며 고른다.
- 짧은 고정 목록(경력, 직군, 고용형태, 기술 스택)은 토글이나 칩으로 보여준다.
- Bot 홈에는 회사 Bot이 없을 때의 빈 상태 UI를 두지 않는다.
- 검색 결과가 없을 때는 화면 전용 "결과 없음" UI 대신 헤더를 뺀 영역 가운데에 짧은 문구를 둔다 (확인 필요: 홈 검색의 결과 없음 UI를 아예 없앨지).
- 설정 행은 값만 보여준다. 예: "한국어", "시스템 테마". 반복되는 라벨과 오른쪽 장식은 두지 않는다.
- 설정 행의 값만으로 뜻이 불분명하면 짧은 이름을 붙인다. 예: "커리어 상태 모두 공개" (확인 필요: 값만 쓸지 이름을 붙일지).
- 메뉴 항목의 아이콘은 같은 계열로 맞춘다.

## 7. Bot 채팅

### AI 우선 채팅

- 채팅 안에서 해결한다. 별도 UI 블록을 만들지 않는다.
  - 이유: 사용자는 Bot과 대화한다. 채팅방에 버튼이 흩어져 있으면 낯설고 뒤죽박죽이다.
- 자세한 내용은 말풍선 안의 회색 보조 글로 두고, 눌러서 펼친다.
- 말풍선 안에서는 마크다운을 쓴다. 표, 목록, 초안이 해당한다. 순서가 있는 목록은 평범한 마크다운 목록이다. 예: 피드백과 단계 요약은 표로 보여준다.
- 초안과 점수를 올린 대상은 결과와 함께 보여준다.
- 이동이 필요하면 말풍선 안에 "이동하기" 링크 글자를 둔다.
- 채팅방 안에는 "바로 지원하기"나 "프로필로 전환" 같은 동작 버튼을 두지 않는다. 다음 동작은 모달이나 액션 시트로 묻는다.
  - 이유: 이런 버튼이 채팅방에 있는 것이 낯설다.
- 빠른 시작 항목은 입력창 위에 캡슐 모양으로 둔다.
- 대상이 필요한 빠른 시작은 모달 하나에서 대상을 고른다. 모달 위에 모달을 겹치지 않는다. 눌러도 소용없는 링크 모양 글자는 두지 않는다.
  - 이유: 링크처럼 보이는 글자는 바꿀 수 있다는 것을 알아볼 수 없다.
- 차이가 없는 빠른 시작은 하나로 합친다. 예: 공고 비교와 적합도 확인.
  - 이유: 둘의 차이가 없다.
- 답만 필요한 빠른 시작은 시트를 열지 않고 Bot이 채팅으로 답한다. 예: 마감 확인.
  - 이유: 선택할 것이 없는 시트는 할 일이 없다.

### 상태 줄

- 상태 줄은 Bot이 응답하는 동안만 보인다. 응답이 끝나면 사라진다.
  - 이유: 상태 줄은 진행 중임을 알리는 중간 상태 UI이고, 한 일을 보여주는 곳이 아니다.
- 상태 줄은 일반적인 진행 문구만 쓴다. 예: "공고 읽는 중", "중지하는 중".
- Bot 로고가 왼쪽에 있고, 로고만 움직인다.
- 순서를 기다리는 상태도 같은 상태 줄 모양에 문구를 보여준다. 예: "순서를 기다리는 중".
- 모든 상태가 같은 상태 줄 UI를 쓴다. 화면마다 다르게 그리지 않는다.
- 완료한 결과와 오류는 상태 줄이 아니라 말풍선이다.
  - 이유: 한 일은 채팅 말풍선으로 보여준다. 오류는 중간 상태가 아니다.
- 주의가 필요하면 헤더의 마스코트에 빨간 불을 켠다.
- 승인은 사용자가 답할 때까지 기다린다. 만료 문구도 만료 상태도 없다.
  - 이유: 승인은 시간이 지나 닫히는 것이 아니다. 만료라는 개념이 없다.
- 서버는 상태 문구를 이 규칙대로 일반적인 진행 문구로 돌려준다. 디자인에 있는 문구는 예시다.
  - 이유: Bot이 무엇을 하는지는 미리 알 수 없어 디자인의 문구는 예시일 뿐이고, 서버가 문구를 돌려줘야 한다.

### 말풍선과 질문

- Bot이 추천한 수정은 묻지 않고 적용한다. 사용자는 결과를 보고 "되돌리기"나 "적용"을 고른다.
- 사용자가 요청한 변경에는 "승인할까요?" 모달을 두지 않는다. 변경 내용을 보여주고 "되돌리기"와 "적용"만 둔다.
  - 이유: 사용자가 원해서 시킨 일이다. 확인하는 곳에는 되돌리기와 적용이 있으면 된다.
- Bot 흐름의 관문은 일반 모달이다. 페이지형 모달이나 스레드 안 블록이 아니다. 질문은 모달 하나에 하나다.
  - 이유: 모달 하나에 질문이 세 개 있으면 안 된다. 비슷한 경우는 모두 같게 바꾼다.
  - 어디에 적용하나: Bot 흐름의 모든 관문과 비슷한 화면.
- 질문의 선택지는 모달 안의 선택 버튼이다.
- 중지, 오류, 취소 안내는 말풍선으로 쓴다. 예: "작업을 중지했어요 · 어떻게 할지 알려 주세요"를 회색으로 쓴다.
- Bot이 자신을 가리킬 때도 "Bot"이다.
- Bot을 쓰려면 내 자료 읽기에 동의해야 한다. 동의하지 않으면 Bot을 쓸 수 없다.
  - 이유: 동의하지 않으면 아예 쓸 수 없다.

## 8. 데이터·날짜

- 공고 마감일처럼 날짜가 있는 항목은 북마크하거나 지원하면 서버가 캘린더에 자동으로 넣는다. 앱은 다시 불러오기만 한다. "마감일 넣기" 버튼은 없다.
  - 이유: 북마크하거나 지원하면 당연히 캘린더에 들어가야 한다.
  - 어디에 적용하나: 앱 전체. 마감일과 같은 날짜 항목 모두.
- 캘린더 연동 같은 설정은 설정 화면에서 한다. 빠른 시작 시트에 "캘린더 연동됨" 같은 상태를 두지 않는다.
- 공고 적합도와 기본 서류는 기본 허브 프로필(내 프로필)로 한다. 다른 서류로 계산하지 않는다.
  - 이유: 공고의 적합도 계산은 기본 허브 프로필로 한다.
- 잠긴 적합도 카드는 실제 막대를 흐리게 보여주지 않는다. 예시 막대를 쓴다.
- 링크는 호스트만 보여준다. 예: google.com. 경로는 보여주지 않는다. GitHub 프로필은 보여준다. "github.com/아이디"로 쓸지 "아이디"만 쓸지는 정하지 못했다 (확인 필요).
  - 이유: 경로를 노출할 필요가 없다.
- 링크 종류는 공고, GitHub, 포트폴리오, 블로그, 기타 다섯 가지다. LinkedIn은 호스트에서 알아낸 표시일 뿐 종류가 아니다.
- 회사 사진은 빠른 시작과 제안 카드 같은 곳에 넣지 않는다.
- 제안에 함께 보내는 공고는 보내는 사람이 지금 다니는 회사의 공고만 가능하다.
- 제안에 붙은 공고는 채팅 스레드 안의 말풍선이다. 상단에 고정하지 않는다. 문구는 "OO님이 OO를 보냈어요"다. 지역, 경력, D-day는 넣지 않는다.
- 삭제한 자료는 30일 보관한 뒤 지운다. 삭제 후에는 되돌리기 토스트를 보여준다.
- 사용량은 계정 화면에 글자로만 보여준다.
- 외부 서류는 앱에서 고치지 않는다. Push 서류만 앱에서 편집한다.

## 9. 계정·권한

- 로그인 방식은 Google, Apple, GitHub, 휴대폰이다. 이메일과 비밀번호는 기업용이다.
  - 이유: 웹과 앱의 로그인 방식이 같아야 한쪽에서 만든 계정으로 다른 쪽에도 들어갈 수 있다.
- 소셜 계정으로 가입한 뒤 인증한 휴대폰 번호는 그 계정의 로그인 수단이다. 같은 번호로 휴대폰 로그인하면 그 계정에 들어간다. "이미 가입된 번호"로 막지 않는다.
  - 이유: 구글로 로그인하고 휴대폰을 인증한 뒤 그 번호로 들어가면 로그인이 되어야 한다.
- Bot 권한 모드(권한/자동) UI는 어디에도 없다. 모드는 자동으로 고정이다.
  - 어디에 적용하나: 앱 전체.
- 개인 계정의 결제는 앱 안에서만 한다. 플랜 화면은 별도 페이지로 열고 결제 버튼을 둔다. "결제 준비 중" 상태는 보여주지 않는다.
  - 이유: 한 계정 유형은 한 결제 경로만 쓴다. 결제 준비 중 UI는 필요가 없다.
- 플랜 안내문은 큰 제목으로 쓰지 않고, 본문 글 사이의 링크 글자로 둔다.

## 10. 예외

- 동의 모달(Bot 만들기, 회사 Bot의 참고 자료 동의)은 얼럿이 아니라 일반 모달이다. 페이지형 Bot 만들기 모달 위에서도 열린다. "모달 위에 모달 금지"의 예외다.
- 개발용 마스코트 갤러리는 제품 화면이 아니다. 이 규칙의 대상이 아니다.
- 앱 화면에서 한 동작이 실패했을 때의 표시는 얼럿, 토스트 어느 쪽이 맞는지 확정하지 못했다 (확인 필요). Bot 채팅 안의 오류는 항상 말풍선이다.
- 수락함 배지의 색은 확정하지 못했다 (확인 필요). 다른 배지는 회색이고 "합격"만 검정이다.
- 설정 행의 값에 이름을 붙일지는 확정하지 못했다 (확인 필요).
- 홈 검색의 "결과 없음" 화면을 없앨지는 확정하지 못했다 (확인 필요).
- GitHub 링크의 표기 형식은 확정하지 못했다 (확인 필요).

## 11. 웹(fo-web)과 다른 점

- 웹은 "에이전트"를 쓰고, 앱은 "Bot"을 쓴다. 같은 기능의 이름이 다르다.
  - 이유: 앱의 제품은 Bot이고, 웹은 같은 기능을 에이전트라고 부른다.
- 공고는 웹에서만 수정한다. 앱은 보내기만 한다.
- 웹의 일반 구직자는 일반 공고 사이트처럼 지원하기와 북마크를 쓸 수 있어야 한다.
- 기업 계정은 이메일과 비밀번호로 로그인하고 결제는 웹에서 한다. 개인 계정은 앱 안에서만 결제한다.
  - 이유: 한 계정 유형은 한 결제 경로만 쓴다.
